# StudyCore — Agent Rules

## Критическое правило: НИКАКОГО КОДА БЕЗ АППРУВА

Перед написанием ЛЮБОГО production-кода пользователь должен явно сказать «да, этот план меня устраивает» или «апрув».

Это правило существует, потому что в прошлом агент показал системный паттерн:
1. Торопился написать код без понимания требований
2. Делал по частям («вот кусочек — посмотри»)
3. Каждая итерация порождала новые баги
4. Модуль календаря (v2.0/v2.1) потребовал неделю итераций и остался с косяками

**Нарушение этого правила = провал модуля.**

## Процесс разработки (обязателен для модулей >3 файлов)

```
┌──────────┐   ┌──────────────────┐   ┌─────────┐   ┌─────────┐
│ SPECIFY  │ → │ DESIGN (+ аппрув)│ → │  TASKS  │ → │ EXECUTE │
└──────────┘   └──────────────────┘   └─────────┘   └─────────┘
   required      required (user ok)     required      required
```

### Phase 1: SPECIFY
- Собрать существующий код и исследования
- Определить user story, acceptance criteria, goals, non-goals
- Создать `docs/[module]/SPEC.md` с traceable requirement IDs (REQ-001, REQ-002...)
- НЕ ПИСАТЬ КОД

### Phase 2: DESIGN — только после полного аппрува пользователя
- Архитектура: data flow, state machine, components
- Модели данных: DB schema, API contracts (Pydantic + TypeScript interfaces)
- Технологические решения с обоснованием
- Сохранить в `docs/[module]/DESIGN.md`
- Показать пользователю. Ждать явного «да».
- НЕ ПИСАТЬ КОД

### Phase 3: TASKS
- Разбить на atomic tasks с verification criteria
- Зависимости между задачами
- Оценка effort
- НЕ ПИСАТЬ КОД

### Phase 4: EXECUTE — только после аппрува TASKS
- Работать строго по списку tasks
- Каждый task: implement → verify (tests) → commit → update progress
- Если task открывает новый вопрос — STOP, спросить пользователя, не додумывать самому

## Auto-Sizing по сложности

| Scope | Примеры | Процесс |
|-------|---------|---------|
| **Small** | ≤3 файлов, одна функция | Quick fix, но всё равно показать план |
| **Medium** | Новый endpoint + UI | Brief spec → inline design → implement |
| **Large** | Модуль календаря | Full spec + design + tasks → implement per task |
| **Complex** | Генерация конспектов, ML pipeline | Full spec + **discuss gray areas** + research + arch + breakdown + **interactive UAT** |

**Модуль генерации конспектов = Complex.** Требует обсуждения gray areas (Whisper, хранение, цена, UX) и interactive UAT после каждого end-to-end flow.

## Интерфейсы первыми, реализация потом

1. Pydantic модели (backend schemas)
2. TypeScript interfaces (frontend types)
3. API endpoint signatures (only stubs, no implementation)
4. Пользователь проверяет структуру данных
5. Только потом — заполнять реализацией

## Один end-to-end flow вместо всего модуля

1. Выбрать ОДИН типичный сценарий (например: одно занятие с HTML-контентом → конспект)
2. Реализовать полный pipeline для него
3. Пользователь проверяет качество и UX
4. Если говно — переделываем один flow, не весь модуль
5. Только когда flow идеален — масштабировать

## Тесты = критерий приёмки

- Каждый task включает test (unit или integration)
- Тест пишется ДО или ВМЕСТЕ с реализацией
- Если pytest не проходит — task не считается выполненным
- Пользователь может запросить: «покажи вывод pytest» — и агент обязан показать

## Handoff при завершении сессии

При любом завершении работы (даже если "продолжим завтра") создавать `docs/handoffs/HANDOFF_YYYY-MM-DD.md` по шаблону из skill `handoff`.

## Запрещённые паттерны

- ❌ "Вот кусочек — посмотри, норм?"
- ❌ "Я додумал за тебя..."
- ❌ Изменение API контракта после того, как frontend его использует
- ❌ Рефакторинг существующего кода ради нового модуля без явного разрешения
- ❌ "Быстренько накидаю, а потом поправим"

## Разрешённые паттерны

- ✅ "Вот план — апрувни, потом напишу"
- ✅ "Вот интерфейсы — ок ли структура данных?"
- ✅ "Вот один работающий flow — проверь качество"
- ✅ "Тесты проходят — вот вывод pytest"
- ✅ "Не уверен — вот варианты, выбирай"
